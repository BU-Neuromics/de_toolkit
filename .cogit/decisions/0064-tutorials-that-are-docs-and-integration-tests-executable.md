# Tutorials that are docs and integration tests: executable Markdown run by pytest, not Quarto

- Proposed by: the planning session, 2026-11-20, on Adam's request for
  tutorials. A choice of tooling within the scope he set, so it may be
  accepted under his delegation (DETK-0063).

## Background

Adam, 2026-11-20, relayed by the driver session: "As part of the
acceptance criteria, I'd like to add several fully functional and
documented tutorial workflows that both serve as user facing docs and as
integration tests. We could use quarto for this if that's a good fit."
So each tutorial is one source that a reader follows on the docs site
and that CI runs, failing when a command or an output no longer matches
what the page says.

## Context

- **Docs:** a mkdocs-material site (DETK-0004), built strictly in CI
  (`mkdocs build --strict`) and published from `docs.yml`; the docs job
  has Python only, no R.
- **The tutorials are shell sessions.** detk is a set of commands; a
  tutorial is a sequence of `detk-*` command lines on files, with some
  R only to fetch data (the airway example's `prepare_data.R`) and Python
  or R only to check results.
- **What exists:** `docs/example.md` narrates the airway pipeline, and
  `examples/airway/run.sh` runs the same commands, copied, with
  `tests/example/test_airway_example.py` running the script in the R
  job. The two copies can drift.
- **CI:** uv-based test jobs (no R) on several Pythons; one job with R
  and Bioconductor from bioconda through micromamba; combined coverage
  with a floor.
- **Criteria:** one source per tutorial (no drift); what the page shows
  is what was checked; runs in the existing CI jobs; renders in the
  existing site; easy for people and coding agents to edit and review
  in a diff; few new dependencies.

## Options

### Option A: executable Markdown pages, run by a pytest collector

Each tutorial is a page under `docs/tutorials/`, plain mkdocs Markdown.
A small collector in `tests/tutorials/` (about a hundred lines, no new
dependency) runs each page as one test: every ```` ```bash ```` block in
order, with `bash -euo pipefail`, in one fresh working directory per
page, so files carry from block to block as they do for a reader. HTML
comments, invisible on the site, mark what the runner needs:

- `<!-- tutorial: requires R DESeq2 airway -->` (or `mlr`) at the top:
  the test is skipped, with the reason, where those are missing, and
  runs in the R job.
- `<!-- tutorial: expect -->` before a ```` ```text ```` block: that
  block is the previous command's output, and the test compares it
  (exactly, or by a pattern for numbers and times).
- `<!-- tutorial: fails -->` before a block: the block must exit
  non-zero (a recipe's check, say), and the output shown is its stderr.
- `<!-- tutorial: hidden -->`: a block that runs but is not shown,
  for a check that would distract a reader (rare; most checks are worth
  showing).

Deeper checks (results against DESeq2 run directly, against numpy) go
in an optional `tests/tutorials/test_<page>.py` that gets the page's
working directory after the page has run.

For: one source; the outputs on the page are checked on every run; it
is the site's own Markdown, so the docs build is unchanged and needs no
R; diffs are plain text; it runs in the existing jobs; it also replaces
`run.sh`'s copy of the airway commands. Against: the outputs shown are
written by hand (then checked), not captured, so a figure on a page is
an image committed from a run, not regenerated by the docs build; the
collector is ours to keep.

### Option B: Quarto

Tutorials as `.qmd` documents rendered by Quarto, which runs the code
and puts the real output, tables and figures in the page.

For: captured output and figures; R and Python both first class; `quarto
render` fails on an error, so a render is a test of sorts. Against, for
this repository:

- Quarto is its own site generator. Either the site moves to Quarto
  (reopening DETK-0004, a scope change for Adam), or `.qmd` files are
  rendered to Markdown before `mkdocs build` and the output committed or
  generated in the docs job, which then needs the Quarto CLI and, to
  execute, R with Bioconductor or a frozen copy of the outputs (frozen
  output is no longer a test).
- Shell code runs through knitr's `bash` engine (needs R, rmarkdown
  and knitr, and each chunk is a fresh shell) or a Jupyter bash kernel
  (another dependency). The tutorials are almost all shell.
- A render checks that commands exit 0, not that their output is
  right; checks have to be written as code in the page.
- It runs outside pytest, so it needs its own CI step, its own skip
  logic for R and Miller, and does not join the coverage report.

Quarto fits best a narrative analysis in R or Python with figures; detk's
tutorials are command lines, which Markdown already shows well.

### Option C: Jupyter notebooks (nbmake, mkdocs-jupyter)

Notebooks with `%%bash` cells, executed by nbmake under pytest and
rendered by mkdocs-jupyter.

For: captured output; pytest integration. Against: JSON files with
outputs make poor diffs and are awkward for agents to edit; a shell
workflow through a Python kernel; two new dependencies; output
checks still have to be written as code.

### Option D: shell scripts plus prose pages

What `examples/airway/` does today. For: simplest. Against: two copies
of every command, which is the drift this request is meant to end.

## Decision

Proposed. The planning session recommends Option A, and that it be
accepted under Adam's delegation (DETK-0063): it delivers what he asked
for (tutorials that are both the docs and integration tests) within the
existing docs site and CI, so it changes neither the 1.0 promise nor
DETK-0004. Quarto, which he suggested, is a good tool for a different
shape of document; the reasons it is not the fit here are under Option
B. If Adam wants rendered figures regenerated on every docs build, that
is the case for Quarto and would be his to reopen.

The tutorials planned for 1.0 (each its own node):

1. **Differential expression on airway** (`docs/tutorials/airway.md`,
   R job): the airway example as an executed page: stats, filter,
   DESeq2 normalization with size factors, VST, outlier flags,
   `detk-de deseq2`, `detk-util annotate` with gene symbols, the report
   and the crate, with the DESeq2 results checked against DESeq2 run
   directly. It replaces the walkthrough in `docs/example.md` and the
   command copy in `examples/airway/run.sh`.
2. **From quantifier outputs to a normalized matrix**
   (`docs/tutorials/quantifiers.md`, every test job, no R): a small
   committed data set of salmon `quant.sf` files (simulated by a
   committed, seeded script, so there is no licence question), gathered
   with `detk-util gather`, tidied against a sample sheet, normalized
   with CPM and TPM, `detk-transform plog`, `detk-stats summary` and
   the report.
3. **Derived covariates and recorded steps**
   (`docs/tutorials/covariates.md`, R job with Miller): a z-score and a
   log of a numeric column of the airway sample sheet (`avgLength`,
   the mean read length in the airway package's column data, which the
   page's data step keeps) and a constant column, with the Miller
   recipes (DETK-0062), a check failing on a bad value, each run through
   `detk-util record`, then `detk-de deseq2` with the derived column in
   the design, and the crate showing the recorded step as the producer
   of the column data.

## Consequences

release/tutorial-harness builds the collector, the `docs/tutorials/`
section and its index, CI wiring (no R tutorials in the test jobs, R
and Miller ones in the R job) and a how-to for writing a tutorial in
`docs/dev/`. The three tutorial nodes follow it, each after the nodes
whose commands it uses, and release/cli-docs comes after them so the
CLI pages and the tutorials agree. Every tutorial page is part of the
1.0 definition of done.
